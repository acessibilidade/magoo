COMPONENT GUIDE

Explore behaviors before defining the interface.

Quick guide for designers

Always consider the context of the application, even when the guidance follows a standard pattern. Interaction design documents intent. Behavior must be verified in the implementation.

When to use

Use to organize sections and show the actual content hierarchy.

What to draw

Show a clear sequence of levels without choosing a level solely for visual size.

How it behaves

Static headings are not controls. Associated links and buttons retain their own behaviors.

What to document in Figma

Annotate each heading’s level and the logical section sequence for reading and navigation.

How to review

Check whether the purpose and states are clear on small and large screens and with zoom. Verify documented behavior in the implementation, including keyboard and screen reader use where applicable.

Interaction Design

Questions to ask when designing components of type Headings.

Important:
Depending on the context in which you build your components, there may be further questions, and some listed here may not be necessary. Assess each case individually.

Designing for "no interaction"

  1. Before navigating the content, can you perceive the page's visual hierarchy?
  2. Does the main heading clearly describe the page or section?
  3. Do subheadings group related content predictably?

Designing for mouse use (any pointing device)

  1. When headings contain links or actions, do actionable components provide visual feedback?
  2. Does the clickable area avoid turning the entire heading into an unclear action?
  3. Does interaction preserve the readability of the hierarchy?

Designing for gesture use

  1. Do headings remain readable on small screens?
  2. Do line breaks preserve meaning and hierarchy?
  3. Do headings with actions have sufficient touch areas?

Designing for keyboard use (any non-pointing device)

  1. Do interactive components inside headings have visible focus?
  2. Does focus order avoid skipping the content hierarchy?
  3. Are static headings kept from receiving focus unnecessarily?

Designing for screen reader use

  1. Can you navigate headings using screen reader shortcuts?
  2. Is the order of heading levels consistent?
  3. Does heading text communicate the section's topic without relying solely on visual style?

Interaction methods

Possible interaction methods for components of type Headings.

Important:
Only the main methods are listed here. Custom components require further study.

Mouse interaction (any pointing device)

  • Static headings require no interaction.
  • Links inside headings should behave as links.
  • Buttons near headings should have clear accessible names.

Keyboard interaction (any non-pointing device)

  • Static headings do not enter the focus order.
  • Links or buttons associated with a heading should receive visible focus.
  • Navigation order should preserve the logical content sequence.

Keyboard (or gesture) interaction + screen reader

  • Use levels h1 through h6 according to the actual hierarchy.
  • Avoid skipping levels without a structural reason.
  • Do not use headings solely for visual appearance.

Gherkin

BDD (Behavior-Driven Development) methodology focusing on three pillars: User Stories, Acceptance Criteria, and Gherkin Syntax (Given, When, Then).

Scenario: Given that I am on a page containing headings

Keyboard navigation

  1. WHEN I navigate a page using the keyboard
  2. I SEE interactive components near headings following the logical order
  3. THEN, when I activate a link or button associated with a heading
  4. I SEE the corresponding action take place

Desktop screen reader

  1. When I use a screen reader on a computer (NVDA, JAWS, VoiceOver) and navigate the component
    • I HEAR the headings and their structural levels.
    • I can navigate headings using screen reader shortcuts.
    • I HEAR a consistent order of sections and subsections.
  2. THEN, when I interact with the component, when applicable
  3. I HEAR or perceive that the corresponding information, state, content, or action is available.

Mobile screen reader

  1. WHEN I use a screen reader on a phone (TalkBack, VoiceOver) and swipe to navigate the component, the following happens:
    • I HEAR the headings and their structural levels.
    • I can navigate headings using screen reader features.
    • I HEAR a consistent order of sections and subsections.
  2. THEN, when I interact with the component, when applicable
  3. I HEAR or perceive that the corresponding information, state, content, or action is available.

Considerations

Considerations for components of type Headings.

  • Choose heading levels based on content hierarchy rather than visual size.
  • Avoid using multiple h1 without a well-defined page structure.
  • Do not replace headings with bold text when they structure content.
