Interaction Design

Questions to ask when designing interactive components of type Switch.

Important:
Depending on the context in which you build your components, there may be further questions, and some listed here may not be necessary. Assess each case individually.

Designing for "no interaction"

  1. Before interacting, can you tell that the component toggles between on and off?
  2. Does the label describe the controlled setting without relying solely on state?
  3. Is the current state visually clear?

Designing for mouse use (any pointing device)

  1. Is there visual feedback on hover?
  2. Does clicking the control or label immediately toggle the state?
  3. Is the state change visually clear?

Designing for gesture use

  1. Does the touch target include the label when possible?
  2. Does tapping toggle the state between on and off?
  3. Is the touch area comfortable?

Designing for keyboard use (any non-pointing device)

  1. Is there visible focus on the switch?
  2. Can the state be toggled with SPACE?
  3. Does navigation with TAB follow the expected flow?

Designing for screen reader use

  1. Is the switch label announced?
  2. Is the switch role announced when used?
  3. Is the on or off state announced?
  4. Is the state change perceptible after activation?

Interaction methods

Possible interaction methods for components of type Switch.

Important:
Only the main methods are listed here. Custom components require further study.

Mouse interaction (any pointing device)

  • Clicking the switch toggles between on and off.
  • Clicking the label should toggle the state when it is associated with the control.
  • The action usually takes effect immediately, without a confirmation button.

Keyboard interaction (any non-pointing device)

  • TAB moves focus to the switch.
  • SPACE toggles the state.
  • ENTER may work in custom implementations but should not replace support for Space.

Keyboard (or gesture) interaction + screen reader

  • The component should expose its name, role, and state.
  • The state must be binary, remaining on/off without a mixed state.
  • The change should be announced through the new state.

Gherkin

BDD (Behavior-Driven Development) methodology focusing on three pillars: User Stories, Acceptance Criteria, and Gherkin Syntax (Given, When, Then).

Scenario: Given that I am on a page containing a switch

Keyboard navigation

  1. WHEN I use the Tab key to move focus to a switch
  2. The focus I SEE is strongly indicated visually
  3. THEN, when I use the Space
  4. I SEE the switch toggle between on and off

Desktop screen reader

  1. When I use a screen reader on a computer (NVDA, JAWS, VoiceOver) and move focus to the component
    • I HEAR the switch's label and purpose.
    • I HEAR that the component is a switch.
    • I HEAR its current state, such as on or off.
  2. THEN, when I activate or change the component
  3. I HEAR or perceive that its corresponding state, value, content, or action has been updated.

Mobile screen reader

  1. WHEN I use a screen reader on a phone (TalkBack, VoiceOver) and swipe to focus the component, the following happens:
    • I HEAR the switch's label and purpose.
    • I HEAR that the component is a switch.
    • I HEAR its current state, such as on or off.
  2. THEN, when I double-tap or use the appropriate gesture to activate the component
  3. I HEAR or perceive that its corresponding state, value, content, or action has been updated.

Considerations

Considerations for components of type Switch.

  • Use switches for binary settings that take effect immediately.
  • If the action requires confirmation, a checkbox or another pattern may be more appropriate.
  • Do not change the label in a way that changes the accessible name and makes the announced state confusing.
